# Refutation: proposal-minimal-core, through the engine and contracts lens

Scope: every Cypher statement against `00`; ingest against `04 section 1`; the five reads against
`04 section 2` and `02 section 4`; the plugin contract; the test plan against `04 section 5`; the
migration steps. Code opened where a contract needed confirming, cited by `file:line` against
`/home/banou/dev/stub`.

Verdicts: HOLDS (the design already satisfies it), FIXABLE (wrong or missing, repairable inside the
design), FATAL (cannot be satisfied without changing one of the proposal's own principles).

---

## (a) The Cypher, against 00

| item | verdict | evidence | what would fix it |
| --- | --- | --- | --- |
| A1. `LINKS` spans only `FROM Media TO Media` | FIXABLE | The DDL in 2.2 declares `CREATE REL TABLE LINKS(FROM Media TO Media, ...)`. 5.6 then says the table "gains `FROM Cluster TO Cluster`", and 5.6, 5.8, 5.9 and 6.2 all match `(:Cluster)-[:LINKS]->(:Cluster)`. Against the declared schema every one of those is a binder error, and `00` records that `conn.query` THROWS on a binder error rather than returning a flag | Declare every pair at CREATE time (`00`: one rel table may span several FROM/TO pairs). A later ALTER to add a pair is not among `00`'s exercised facts and must not be assumed |
| A2. Identity's candidate scan uses `UNION ALL` with untyped empty lists | FIXABLE | 5.5 unions a branch returning `collect(DISTINCT tp.scope)` (STRING[]) and `collect(DISTINCT {score, count})` (STRUCT[]) against a branch returning `[] AS targetScopes, [] AS targetCounts`. `UNION ALL` is not in `00`'s exercised list at all, and `00` is explicit that params are strictly typed with no implicit cast | Two queries, unioned in JS. The claim costs nothing: both branches already land in the plugin's memory |
| A3. `WHERE ($uris IS NULL OR ...)` in 6.1 | FIXABLE | A LIST param that is sometimes NULL has no inferable type, which is the exact hazard `00` names ("a STRING param into a DATE column is a binder error"). The whole-store fallback (`04 section 6` contract 6) is the path that depends on it | Two statements, one per branch, chosen in JS |
| A4. `NOT a.attached` drops rows whose `attached` is NULL | FIXABLE | 6.1 filters `AND NOT a.attached`; `Aggregate.attached BOOLEAN` is written by 5.9 and any aggregate written before `attached` was computed, or by a plugin that left it unset, has NULL, and `NOT NULL` is NULL, so the row vanishes from every listing. This is the listing contract (`04 section 6` contract 6) failing silently | `coalesce(a.attached, false)`, plus a test that an aggregate with no `attached` still lists |
| A5. 6.1 aliases a returned column `_id` | FIXABLE | `00`: returned nodes carry `_label` and `_id {offset, table}`, and `ORDER BY` on an alias that shadows a node variable already fails ("Order by NODE is not supported"). Aliasing a column to the engine's own reserved name is an unforced risk in the query that runs on every page | Return `a.clusterId AS clusterId` and rename at the JS boundary |
| A6. 3.4's filtered variable length path matches nothing | FIXABLE | 3.4 presents `MATCH (a:Media)-[e:LINKS*1..8 (r, _ \| WHERE r.kind = 'SAME_AS' AND r.by = 'plugin:identity')]-(b:Media)` as "the one recursion in the design", but 5.5's **Produces** list is `Cluster`, `MEMBER_OF`, `VERDICT`, `LINKS:PART_OF`. Identity never writes a SAME_AS `LINKS` row, so the filter matches zero edges; and 5.5 actually computes membership with "union-find in JS over the accepted candidates". The only showcased use of the engine feature `00` measured is dead. Separately, `*1..8` truncates a cluster of more than nine members | Delete 3.4's query and say plainly that membership is a JS union-find over the scan's rows, or have identity emit its accepted SAME_AS edges and drop the JS union-find |
| A7. 5.7's profile scan self-joins membership for nothing | FIXABLE | `MATCH (m:Media)-[:MEMBER_OF]->(c:Cluster)<-[:MEMBER_OF]-(n:Media)<-[:DESCRIBES]-(p:Payload)`: `m` appears in no `WITH`, no filter and no `RETURN`. The pattern produces members x members x payloads rows per cluster before `collect(DISTINCT ...)` collapses them | Drop `m` |
| A8. 5.8's scan groups by a LIST and collects twice over an OPTIONAL MATCH | FIXABLE | `WITH rc, collect(...) AS members` then `WITH rc, members, k, collect(...) AS lent` uses `members` (a large list) as a grouping key, and a cluster with no container yields one row whose collected struct is all NULL rather than an empty list | Key on `rc.id`, re-join members in JS, filter the null container row |
| A9. **The read budget is met and the write path breaks it** | FATAL as written, FIXABLE by restructuring | P6 and `00`'s read costs are honoured on the read side (6.1 is one query, 6.2 is two). But 5.8 and 5.9 are both specified as "one query per dirty cluster", and 5.9 cites `00`'s "60 cluster page in ONE query, 49 ms" as "the per-cluster slice of that", which inverts the measurement: the measured number is one query covering sixty clusters. On `00`'s own session graph (1,000 clusters) a cold listing makes nearly every cluster dirty, so an aggregate pass is at least 1,000 round trips at `00`'s 1 to 2 ms floor, 1 to 2 seconds of round trip alone, plus a range pass, times up to 3 passes (5.2), retriggered on every DataLoader flush (50 ms, `04 section 1.3`) | One query per plugin per pass over `UNWIND $dirtyIds`, field merge in JS, one `UNWIND` write back (`00`: 18x for batched writes). This is a restructuring of 5.8 and 5.9, not a tweak, and the cost story in 11.1 has to be rewritten around it |
| A10. Reconcile reads the whole materialized view every pass | FIXABLE | 5.5 reconciles `MEMBER_OF` and `VERDICT` "without scope: the plugin recomputes the whole membership every pass", and 11.1 says "the reconcile diffs in JS". Diffing in JS means reading every row the plugin owns first: on `00`'s session graph that is ~5,796 `MEMBER_OF` plus ~7,896 `VERDICT` rows pulled across the nested worker boundary per pass | Keep a JS-side mirror of each plugin's own output keyed by natural key, or diff with a server-side anti-join |
| A11. Every read deserializes JSON blobs | FIXABLE, unmeasured | `00` says JSON "reads back as a string". 6.1 returns `a.fields` and `a.handles` per row, so the whole-store fallback parses a full `Media` per cluster on every 100 ms-debounced event (`04 section 3`). `00` measured query time, never transfer or parse across the nested worker's postMessage. Today the same read hands back live objects | Measure it in migration step 2 against the old store on the same replay; promote the listing's handful of fields to columns if it costs |
| A12. `MERGE` on the primary key, `UNWIND` batching, multi-statement writes, `DELETE e` by `by` | HOLDS | All four are exercised in `00` and the ingest (4.1) and `reconcile` (5.1) use them the way `00` measured them |

## (b) Ingest, against 04 section 1

| item | verdict | evidence | what would fix it |
| --- | --- | --- | --- |
| B1. **`useOnResolve` also fires on `MediaHandle.node`, so nested handle nodes DO become payloads** | FATAL for 4.2 as written, FIXABLE by changing the trigger | The hook keys on `getNamedType(info.returnType).name === 'Media'` (`src/worker/extractor.ts:473-479`), and `MediaHandle.node: Media!` (`src/worker/resolvers/media/schema.gql:226-231`). The media modal selects handle nodes two levels deep (`src/router/home/media-modal.tsx:429-445`), so those fields ARE resolved and each nested node arrives at `mediaInserter.load`. Under 4.1 each becomes its own `Payload` with `uri` = the nested node's uri and `origin` = the ANSWERING server, which is a partial row of another source's id under a third source's origin: `01 I5.3` exactly, the defect 4.2 promises is now impossible ("a nested handle node never becomes a row"). 9.1 says the hook stays "unchanged", so the design's own ingest contradicts its own invariant | The hook must key on POSITION as well as type: refuse the load unless `info.parentType` is the subscription root (or `MediaPage`). That is a change to the one trigger 9.1 lists as untouched, and it changes what `Media.episodes` on a handle node writes too, so it needs its own test with a control (a nested node that must NOT produce a payload) |
| B2. The decomposition round trip cannot be byte exact | FIXABLE | 4.1 step 3 keys `CLAIMS` on (payload key, target uri, relation, depth) with no ordinal. Two handles at one depth naming one uri with one relation but different `node` JSON collapse to one edge, and 9.3's core test ("the decomposition round-trips byte for byte") then fails or is quietly weakened | Add `ordinal INT64` to the key and to the edge |
| B3. The step 1 dual write can reject the shared DataLoader batch | FIXABLE, high cost if missed | `00`: `conn.query` THROWS on a binder error. A DataLoader batch function that rejects rejects every key in the batch, and `04 section 4.3` records exactly that happening on the deployed site on 2026-09-05: "THE SHARED INSERT BATCH REJECTED FOR EVERY EXTRACTOR IN IT, first-party sources included". Step 1 says "call it from the three DataLoaders **beside** the old `upsert*` calls" and never says the call is isolated | Wrap the new ingest in a try/catch that logs and returns, with a test that a throwing ingest leaves `upsertMedia`'s result unchanged |
| B4. A content-hash payload key turns any array-order instability into a permanent event loop | FIXABLE, unmeasured | 4.3's no-op rests on byte identity, and the round trip (B2) forbids canonicalizing array order. A source whose `titles`, `episodes` or `genres` order is not stable between fetches mints a new payload on every re-fetch, which moves `seq`, runs a pass, emits `graph:changed`, re-reads every page and re-asks every origin: the loop `tests/unit/worker/store/edge-idempotence.test.ts` exists to stop (`04 section 3`, "an event that fires when nothing changed is not free"). The media page re-asks every origin and the loader flushes every 50 ms, so the retry rate is high | Probe it before step 1, not after: fetch each source twice in one session and compare canonical hashes per (origin, uri, operation). Where it is unstable, either sort the array at ingest and record that the round trip is order-insensitive for it, or key the payload on a field subset |
| B5. The synthetic `ASK` payload is invisible to identity's scan | FIXABLE | 4.1 step 5 creates a payload whose `raw` is the question and a `CLAIMS` edge from it, but never says it writes `DESCRIBES`. 5.5's scan opens `MATCH (p:Payload)-[:DESCRIBES]->(s:Media), (p)-[c:CLAIMS]->(t:Media)`, so with no `DESCRIBES` the consumer's claim is never evaluated and the similar consumer contributes nothing. If it DOES write `DESCRIBES`, its NULL `scope`/`score` join the anchor's own payload evidence in rule I1 and a synthetic payload starts counting as "an own payload exists" | Write `DESCRIBES` and add a `synthetic BOOLEAN` that every evidence collector filters out, with a test per collector |
| B6. A claim before its row, and a re-fetch of the same uri | HOLDS | Anchors are created on first NAMING (4.1 step 1), so a claim to an undescribed uri lands as an edge and identity I2 defers it. This is `pendingClaims` (`02 section 2.4`) with no queue and no expiry leak (`02 section 5.3`), and it is a genuine simplification |
| B7. Episodes arriving without their media or before it | HOLDS | 4.1 step 4 hangs `HAS_EPISODE` off the anchor named by the episode's own `mediaUri`, MERGEd whether or not that media has a payload. Matches `db.ts:406` semantics without the ordering dependency |
| B8. The fan-out still discards payloads; the graph is the only join | HOLDS | 4.1 keeps it (`04 section 1.5`), which is what makes the flagged migration possible at all |
| B9. Batches of 250 on a 50 ms timer | HOLDS | 4.1 keeps both and writes three `UNWIND` statements per batch in one multi-statement query, both exercised in `00` |

## (c) The read contracts, against 04 section 2 / 02 section 4

| item | verdict | evidence | what would fix it |
| --- | --- | --- | --- |
| C1. **P3 (retraction) against contract 2 (`Media.uri` only grows)** | FATAL | `shouldGrowAddress` rewrites the address only when the cluster in hand shares a member AND has STRICTLY MORE handles (`src/utils/uri.ts:143-149`, `matchAggregatedUris` at `:266-275`). P3 makes a member leaving a cluster routine ("cluster membership is recomputed from claims on every pass"), so `ag:(...)` can shrink. The address then keeps naming a member the cluster no longer holds, 6.2 resolves that address with `UNWIND $uris ... LIMIT 1` and can land on whichever cluster the departed member went to, and the page silently becomes a different work. The same path is shared between viewers by the party protocol (`04 section 2.3`). On top of that, urql keys `Media` on `_id` (`src/urql-keys.ts:17`) and identity I8 gives the id to the larger part, so the smaller part remounts every card mid-session. `04 section 6` contract 1 and 2 are both written on the assumption that neither can happen | Either membership is monotone WITHIN a session (P3 becomes "reversible across a reload", which is most of its value and none of its cost), or the design needs a published-identity rule: once an aggregate has been handed out, its uri and `_id` are pinned for the session and a retraction shows as a redirect. Both are principle-level changes and the owner has to pick one |
| C2. `Aggregate.handles` cannot satisfy `MediaFragment` | FIXABLE | 2.2 and 5.9 define `handles JSON` as `[{relation, uri, url, origin}]`. `MediaFragment` selects `handles { relation node { _id uri origin id url } }` (`04 section 2.3`), `Media._id: String!` and `MediaHandle.node: Media!` are both non-null (`src/worker/resolvers/media/schema.gql:226-235`), so a node with no `_id` errors the field and non-null propagation nulls the handle, the handle list and then the whole media. Today `sameAsHandle(mediaToGQL(member))` supplies `_id`, `id`, `episodes: []`, `handles: []` (`src/worker/store/aggregate.ts:86`, `:154-186`) | Store the node SHAPE in the JSON, not four fields, and pin it with a document-level test that runs `GetMediaModal` against a seeded graph |
| C3. `EpisodeSlot.members` cannot serve the watch page | FIXABLE | 2.2 defines `members JSON` as `[{uri, origin, ownNumber, via}]`. The watch page selects `handles { relation node { ...EpisodeFragment url embedUrl mediaUri episodeNumber titles shortDescriptions } }` and builds one release per SAME_AS handle (`04 section 2.3`), and `EpisodeFragment` itself is `_id uri origin id url mediaUri` plus handles (`src/worker/resolvers/episode/fragment.ts:4`). The lent Crunchyroll episode that 6.4 promises as "a SAME_AS handle on the episode slot" has nowhere to carry `embedUrl` | Same fix as C2: the slot's members are episode node shapes |
| C4. A handle node's own `handles` and `episodes` are unspecified | FIXABLE | The modal asks each handle node for its own `handles { node { ...MediaFragment episodes } }` and its own `episodes` (`GET_MEDIA_DETAILS`, `src/router/home/media-details.tsx`). Today both resolve to `[]` because `mediaToGQL` sets them empty (`aggregate.ts:181-182`), which is why the two-level selection is cheap. The proposal never says what they resolve to; if a handle node resolves through its member's cluster it returns the WHOLE slot list under every badge, once per badge | State it: a handle node is a leaf, `handles: []` and `episodes: []`, and pin it, because the cost of getting it wrong is N+1 slot queries inside one modal |
| C5. 6.2 loses `findMediaForPage`'s ORDER | FIXABLE | `db.ts:349-364` tries each handle uri IN ORDER, preferring the first that names a RUN and otherwise keeping the first non-empty. 6.2's `UNWIND $uris AS u ... ORDER BY CASE WHEN c.scope = 'RUN' THEN 0 ELSE 1 END LIMIT 1` orders only on scope, so between two RUN members the winner is engine order. That breaks `01 I15` and `container-page.test.ts`'s "earliest first" | `UNWIND range(0, size($uris)-1) AS i` and order by `i` after the scope key |
| C6. `attached` is global where `hideAttachedContainers` is per list | FIXABLE (or state it as an intended change) | `db.ts:391-398` drops a container only when a run cluster IN THE SAME LIST points at it ("Run clusters always survive"). 6.1's `NOT a.attached` is a global property, so on the narrowed-uris path a container whose run is not on this page is now hidden where today it renders as a card. Step 3's gate is "the listing renders identically under the flag", which this makes false | Either join `attached` per read (a second hop, cheap on materialized membership) or write the difference down and change the step 3 gate to name it |
| C7. `applyMediaFilters` runs after the container cut | HOLDS | 6.1 filters `NOT a.attached` inside the query and applies `applyMediaFilters` in JS afterwards, which is the order `media/index.ts:133-136` requires. `filter.test.ts`'s reference-identity pin survives because the filter still runs over JS objects |
| C8. `searchKey` as stripped titles | HOLDS | `searchScore` strips BOTH sides itself (`src/sources/utils.ts`), so precomputing `stripTitle` changes no score and the 0.7 relevance threshold and the 0.44 catalogue threshold are untouched. | C9. `exportGraph` has no `Media` rows to publish | FIXABLE, and it is bigger than one line | `StoreExport.clusters[].members` is `Media[]` (`02 section 1`, `export.ts:5`), and `sources/offline/seed-build.test.ts` is literal against that shape (`04 section 5.3`). There are no merged rows any more, only payloads, so reconstituting a member row IS `plugin:aggregate`'s per-origin merge, which is plugin output. `exportStore`'s own promises are "it reads, and never writes ... never a union the fuzzy pass made" and byte-identical between two calls (`02 section 4.8`); an export that reads a plugin's table breaks the second and blurs the first. Separately, today's walk is over ASSERTED pairs that survived the scope derivation and whose ROWS EXIST (a deferred claim counts only once its row lands, pinned by `export.test.ts`), where a raw `CLAIMS` walk reaches anchors nothing describes | Define the export's own member projection (the per-origin merge, as a pure function shared with `plugin:aggregate` but called directly, never read from its table), and restate the two refusals over anchors that have at least one non-excluded payload |
| C10. Aliasing `media:changed` and `episode:changed` to `graph:changed` | FIXABLE | `Subscription.media` listens to BOTH with no debounce (`media/index.ts:40`), so one pass wakes it twice and re-runs `read()` plus `askUnasked` twice. `04 section 3` records that an event that fires for nothing is not free | Emit `graph:changed` only, and move the two listeners in the same step; the alias is a shortcut that doubles the wake rate on the one subscription that has no debounce |
| C11. `waitForMedia` now waits for a completed pass | SERIOUS, priced nowhere | `04 section 1.8`: seven call sites block inside a source resolver on `ctx.findAggregatedMedia` with 15 s or 30 s deadlines. 6.2 answers "from the last completed pass" (11.1). | C12. Contract 5 (an empty read yields nothing) and contract 6 (the whole-store fallback) | HOLDS | 6.2 yields nothing and relies on the pass event; 6.1 keeps the fallback. The event finally carrying cluster ids closes `04 section 3`'s "declared and never populated" |

## (d) The plugin contract

| item | verdict | evidence | what would fix it |
| --- | --- | --- | --- |
| D1. **The check disables `plugin:identity` on the first cold load** | FATAL as written | 5.4 reads source-table counts before and after each plugin's `run` and, on a difference, "deletes every row `WHERE by = $plugin AND seq = $now`, disables the plugin for the session and reports it". The worker is one JS thread, but a pass is nothing but awaits on the nested engine worker (`00`: every call is an async round trip), so a DataLoader flush (50 ms, `04 section 1.3`) lands its three ingest statements DURING the pass. The counts then differ for a reason that is not the plugin, and the first plugin in the order is `plugin:identity`. On a cold season page with 24 sources answering, this is not a possibility, it is the normal case | Compare only rows with `seq <= passStart`, or record the ingest's own write counter and subtract it. And the runner test in 9.3 ("a plugin that writes through `query` is caught by the check", the control that must fail) has to be paired with a control that INGESTS during the pass and must NOT fail |
| D2. The check does not cover what it claims to cover | FIXABLE | 5.4 counts `Payload`, `CLAIMS`, `Media`, `Episode`, `HAS_EPISODE`. It does not count `DESCRIBES` or `Origin`, both source tables (2.3), so a plugin deleting `DESCRIBES` passes. `count + max(seq)` also cannot see an in-place `SET` (admitted in 5.4) nor a delete-plus-insert that preserves both numbers. So P4's "the core checks the source tables after every plugin" is a smoke alarm presented as a proof | Enforce by capability rather than by audit: the plugin's `query` refuses any statement carrying a write clause, proven by a control plugin in the suite whose write MUST be refused. Keep the count check as the backstop and extend it to every source table |
| D3. **No termination argument** | FATAL | `02 section 2.7` and `04 section 2.1` record that today's loop terminates because the union-find is monotone ("the cluster only ever gains members (union-find unions, it never splits), so each source is asked at most twice"). P3 deletes monotonicity and 5.2 replaces the argument with "up to 3 passes per trigger", with 11.1 adding "an idle pass when no ingest arrives for 500 ms". A cap truncates, it does not converge. `plugin:title`'s profile (titles, `linkUri`, seasons, days) is a function of membership, and the link it emits changes membership, so a two-cycle is available; under the idle re-trigger it oscillates forever, emitting `graph:changed` each time, waking every subscribed page and re-asking every source, with `_id`s flipping between the two shapes. Nothing detects it, and the aggregate the user sees depends on where the cap fell | Hash the plugin-table state at the end of each pass and stop on a repeat, reporting the cycle with the clusters in it; or restore monotonicity within a trigger (accepted links may only be added inside one trigger, retraction happens at trigger boundaries). Either way this needs a written argument, not a number, because it is the only thing standing between the design and an unbounded re-read loop |
| D4. A plugin that throws mid-run is unspecified | FIXABLE | `reconcile` is called several times per run (per cluster in 5.6, 5.8, 5.9). There is no transaction in `00`'s exercised set. A throw after the third of twenty reconciles leaves membership half-rewritten and the aggregates computed against it, and 5.4's recovery (delete by `by` and `seq = now`) restores nothing it DELETED | Say what happens: either one transaction per pass (and verify the engine supports it, it is not in `00`), or reconcile stages into a shadow set and swaps at the end of the run, or the runner marks the plugin's output stale and reruns from scratch next pass |
| D5. Two plugins can hold the same natural key, and the ordering rule contradicts itself | FIXABLE | `Produced` (5.1) lets any plugin write `Cluster`, `MEMBER_OF` and `LINKS:SAME_AS`. `LINKS.key` is "kind + from + to + fromEpisode" with no `by`, so two plugins can hold two rows with one key and `reconcile` (which diffs "the rows this plugin already holds") never notices. Separately 5.1 says "a cycle is a startup error" and then sanctions the identity/title cycle as "the one the runner allows" | One declared writer per table, checked at registration; `by` in every natural key; and the identity/title loop declared explicitly as a two-phase pair rather than as an exception to the rule that detects cycles |
| D6. `VERDICT` cardinality contradicts itself | FIXABLE | 2.2 says "One per claim per pass in which it was evaluable"; 5.1 says `reconcile` diffs `VERDICT` by the natural key `claim`, which keeps one row per claim. The first is unbounded over a session (7,896 claims x every pass) | Pick the second and say so; keep the pass number as a property |
| D7. `reconcile(scope: {where: string})` hands a plugin raw Cypher | FIXABLE | 5.1 interpolates a plugin-supplied `where` string into a DELETE. That is the one place a plugin reaches the write path without going through `query`, and D2's audit is the only thing behind it | A structured scope (a table, a column, a value list), never a string |
| D8. Retraction and recompute are idempotent by construction | HOLDS, with one caveat | `reconcile` diffing by natural key, plus 5.3's rule that a plugin never reads its own output as truth, plus 9.3's automatic second run asserting `{added: 0, removed: 0}` on every plugin test, is the right shape and is stronger than anything the current store has. The caveat is I8 (id survival), which 5.3 correctly names as the one read of its own output; it needs its own test that a second run keeps the same ids |
| D9. A plugin's whole output is retractable by its stamp | HOLDS | `00` exercised `DELETE e` on edges selected by `{by: 'plugin:range'}`, which is exactly what 5.1's "reconcile `[]` with no scope" needs |

## Summary

### Fatal

1. **The check disables the core plugin under its own normal load (D1).** A DataLoader flush lands during a pass, source-table counts move, and 5.4's specified response is to delete the plugin's output and disable `plugin:identity` for the session. The design's proof that a plugin never touched a source row is also the design's most reliable way to break itself.
2. **No termination argument (D3).** The monotone union-find was the only thing that made today's read/merge/re-read loop terminate (`02 section 2.7`, `04 section 2.1`). P3 removes it and 5.2 substitutes a cap of 3 passes plus an idle re-trigger, which truncates rather than converges and admits a permanent oscillation with `graph:changed` firing on every cycle.
3. **P3 against contract 2 (C1).** `shouldGrowAddress` (now `shouldRewriteAddress`, `src/utils/uri.ts`) and the urql `_id` key are both built on clusters only ever growing. Routine retraction shrinks `ag:(...)`, strands the address on a departed member, and lets 6.2 resolve one shared link to a different work. Either the reversibility principle is scoped to reloads or published identity is pinned, and only the owner can choose.
4. **The design's own ingest defeats its own invariant (B1).** `useOnResolve` keys on the named type, and `MediaHandle.node` is `Media!`, so nested handle nodes reach `mediaInserter` and become payloads under the answering source's origin. 4.2 promises this cannot happen while 9.1 promises the trigger is unchanged. One of the two has to give, and the fix is a change to the trigger.

### Serious

- The per-cluster query pattern in 5.8 and 5.9 breaks the design's own read budget on the write side, and it cites `00`'s one-query-for-60-clusters measurement backwards (A9). Reconcile additionally pulls the whole materialized view into JS every pass (A10).
- `LINKS` is never declared over `Cluster` pairs, so every cluster-level query in 5.6, 5.8, 5.9 and 6.2 is a binder error against the schema in 2.2, and `00` says a binder error throws (A1).
- `Aggregate.handles` and `EpisodeSlot.members` are four-field records where the app selects a `Media!` and an `Episode!` with non-null `_id` (C2, C3). As written, the modal and the watch page go blank, which is the exact failure shape `04 section 4.3` already paid for once.
- `exportGraph` has no member rows to publish and no projection that does not read plugin output, while the seed builder is literal against `Media[]` (C9).
- The step 1 dual write can reject the shared DataLoader batch and take first-party sources down with it (B3), the precedent being on the record.
- 3.4's filtered variable length path, presented as the design's one recursion, matches nothing that 5.5 produces (A6).
- `waitForMedia`'s seven blocking call sites now wait on a completed pass with no latency budget attached (C11).
- The check covers five of seven source tables and cannot see a `SET` (D2); a throwing plugin has no defined recovery (D4); two plugins can hold one natural key (D5).
- `store/consensus.test.ts`, the largest KEEP block in the worker tree, cannot be verbatim once `alignmentOffset` is generalized and `runEpisodes` is split (E2).

### Minor

- `UNION ALL` with untyped empty lists (A2), the nullable list param in 6.1 (A3), `NOT a.attached` on NULL (A4), the `_id` column alias (A5), the dead self-join in 5.7 (A7), the list grouping key in 5.8 (A8).
- No ordinal on `CLAIMS`, so the byte-exact round trip test cannot pass (B2); the synthetic `ASK` payload has no `DESCRIBES` (B5); array-order instability turns the content hash into an event loop (B4).
- 6.2 drops `findMediaForPage`'s ordered fallback (C5); `attached` is global where the cut is per list (C6); the event alias doubles the wake rate on the undebounced subscription (C10); a handle node's own `handles` and `episodes` are unspecified (C4).
- `VERDICT` cardinality contradicts `reconcile` (D6); `reconcile`'s scope is a raw Cypher string (D7).
- The 55-verbatim count (E1), the corpus replay's shape (E3), the missing `04 section 5.5` suites (E4), step 1's estimate (F1), step 2's singleton arm (F3), step 6's sequencing (F4), and the two unmeasured numbers with no step that measures them (F5).

### Holds

- **Anchors on first naming replace `pendingClaims` outright** (B6). A claim to an undescribed uri is an edge to an anchor, and identity I2 defers it. That removes a Map, its keying scheme and its no-expiry leak (`02 section 2.4`, `02 section 5.3`) and is the cleanest simplification in the proposal.
- **Claims as edges from the payload that carried them** give the store provenance it has never had: `ASSERTED_LABELS` today records only THAT a pair was claimed, never by which payload or when (`02 section 5.1`), and `linkPartOfPairs` records nothing at all.
- **Materialized `MEMBER_OF` instead of a recursive component read** is the call `00` supports (1.7 ms against 6.8 ms, and 1,033 ms on a dense graph), and the read path in 6.1 and 6.2 genuinely is one and two queries.
- **The ingest side is left alone** (9.1): `useOnResolve`, the fan-out discarding payloads, the three DataLoaders' timing, the request context, `enforcePluginOrigin` and `readPluginHandles`. That is what makes a flagged, reversible migration possible, and steps 1 to 5 do leave the app running (F2).
- **`applyMediaFilters` after the container cut, and `searchKey` via `stripTitle`** both preserve the pinned semantics exactly (C7, C8); `searchScore` strips both sides itself, so no threshold moves.
- **The range form as literal properties**, one edge per contiguous segment with `toEpisode - fromEpisode = mapsTo - mapsFrom`, answers `01 case 15` without repeating `01 R1`'s arithmetic placement, and 8.3 and 8.4 correctly mint nothing.
- **The owner's prohibition is structural, not a check**: membership is the closure of accepted SAME_AS only, and nothing crosses `PART_OF` or `INCLUDES` except a proven range (3.4, 7.3).
- **Retraction by stamp and reconcile-by-natural-key** (D8, D9) match what `00` exercised and give every plugin an inverse, which is the property the current store is missing in four separate places.
