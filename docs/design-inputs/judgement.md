# Judgement: the three proposals for stub's new representation

Judged against the owner's brief and the five inputs (`00` engine facts, `01` cases, refutations and
invariants, `02` current store, `03` source capabilities, `04` consumers and tests), with the six
refutations in hand. Four code facts that several verdicts turn on were re-read in the tree and are
cited by `file:line` where they decide something.

The verdict in three lines: **product-first is the base.** Its skeleton (an append-only answer log with
an owner rule on the merged row, one writer with a guard list and a downgrade, six plugins that map onto
the brief's named defaults, a slot read that cannot be handed a container, and a trace panel) needs the
least surgery. It takes fourteen grafts, most from evidence-first (the `containing` answer, the split
veto, recorded silent gates, the invariant queries, the rewired exchange-rate rigs, typed evidence
declarations) and three from minimal-core (the scoped reconcile contract, content-hashed answers, claim
precedence classes). Six owner decisions remain, all of them changes to the schema or to the plugin
contract.

## 3. The verdict: product-first, with grafts

### Why product-first is the base

1. **It is the only one that already has the two shapes the other two are missing.** One writer with a
   guard list and a downgrade (the RUN versus CONTAINER exchange stated once, `02 section 3` items 4
   and 5) is what `01 cases 2 and 7` ask for; evidence-first spreads it across `claims`, `vetoes` and
   `membership`, minimal-core has it as identity rules I1 to I8 with a JS union-find. And the `Answer`
   log with `fieldSeq` and `supports` chains is the only mechanism proposed that turns a production
   bug into a replayable fixture (`02 section 5.2` says this is impossible today).
2. **Its six plugins are the brief's plugins.** Direct edge merging, title matching, season and episode
   range matching, plus profile, containment and aggregate. Evidence-first's fifteen are a finer
   decomposition with a fifteen-step round, back edges and a repeat step; the owner asked for
   "simpler and easier to reason about".
3. **Its fatals are cheap once grafted.** PF-2 is a schema addition the other two already carry; PF-3
   is a downgrade rule; PF-4 is minimal-core's reconcile; PF-1 is one deleted rule plus a parity
   statement. Evidence-first's fatals are also cheap, but its serious list is longer and deeper in the
   queries (scope null, key collision, `title-match` unable to mint the cross-scope `PART_OF` its own
   walkthrough depends on, `episode-number` regressing `01 case 19`, rule B dead for Crunchyroll).
4. **Its read path and walkthroughs are closest to today's contracts.** Resolve then members then slots
   reproduces `findMediaForPage`, `preferAttachedRun` and the SAME_AS-only episode walk, with the slot
   read structurally unable to receive a container's uris (`04 section 2.1`'s "most dangerous read").

What product-first loses without the grafts: containment as a first-class evidence object (the
`containing` answer), the queryability of vetoes (`skipped:absent`), the invariant queries, the
exchange-rate rigs, and the write contract's scope.

## 4. Decisions only the owner can make

Each changes the schema or the plugin contract. Everything else is decided in section 5.

1. **What an address-bar handle may assert** (`01 case 8`, open problem 2; all three proposals raise
   it). *Recommend*: an `address` claim is consumed only when the claimer's own row is one endpoint (a
   source saying "I resolved myself out of this cluster": Crunchyroll's season row to `anilist:X`), and
   is subject to every guard like any claim; an `address` claim relating two rows both foreign to the
   claimer (a bookmark rebroadcast between siblings) is a pointer that routes re-asks and never enters
   the closure. *Why*: `buildHandlesFromUri` is the ONLY attach path for crunchyroll, unogs, appletv
   and justwatch rows resolved through an aggregated uri (`03`), so a pure pointer rule turns every
   such row into a singleton and, under G7, a hidden or orphan card; the stale show-level `cr:` of
   `01 case 6` is already CONTAINER and rides `PART_OF`, and two old season links in one uri are two
   ids of one origin that guard 4 refuses. *Cost of pure pointer*: an unpriced number of duplicate
   season cards. *Cost of full assertion*: the re-injection path stays open, bounded only by the scope
   derivation and guard 4.
2. **`similarMedia` returns `{ media, containing }`** (G1). *Recommend* yes. *Why*: it is the fetch
   that `01 case 12`'s measured win needs once the media-path lend goes, and it lets unogs and
   JustWatch say "this season holds your run" without lying about sameness (`01 case 9`). *Cost
   otherwise*: the lend hack stays permanently in one extractor, and the fold is never visible for
   Netflix or JustWatch.
3. **`MediaHandleRelation` gains `INCLUDES`** as an output value (a run's page lists the seasons that
   hold it, a run split across seasons lists them, a container page lists its seasons) and as a source
   claim fenced to one id space (G15). *Recommend* both. *Why*: without the output value the split
   direction (`01 case 10`) has no rendering; without the fenced source claim unogs's seasons never
   enter the graph for a refused ask. *Cost otherwise*: the split renders as nothing, and the
   container page cannot list seasons. It is a client-visible enum change; the badge reader takes
   "SAME_AS first then anything" and playback takes SAME_AS only (`04 section 2.3`), so no button
   can come from it.
4. **The optional evidence fields on the source schema and on `PluginSourceMeta`** (G10). *Recommend*
   yes, all optional, kitsu and jikan first for `startDatePrecision` (`01 case 34`'s measured 30 day
   error). *Why*: every per-origin table inside the profile plugin is `01 case 44`'s mistake in a new
   place (a constant standing in for a per-claim property), and `01 case 33` priced the field at
   "touching every extractor", which optional fields avoid. *Cost otherwise*: the per-origin tables
   stay hard-coded at parity and the genuine January 1 premiere stays invisible (0.52%).
5. **`provenance`, `anomalies` and `kind` as public fields on the aggregated `Media`, and the
   `?trace=1` panel in production builds.** *Recommend* yes. *Why*: they are the debugging story the
   brief asks for ("easy to trace changes"); each is one field on a type the app already keys, plus a
   `MediaFieldProvenance` entry in `src/urql-keys.ts` keyed `null` like every other embedded type
   (`04 section 5.5`). *Cost otherwise*: the trace stays a dev-only osra method and a bug report stays
   a screenshot.
6. **Merge plugins are first-party only, or a third-party surface.** *Recommend* first-party only for
   this design. *Why*: the isolation argument rests on the applier being the only writer and on the
   harness hashing source tables; a third-party plugin would need the query facade to be a hard
   boundary and its own measurement, and remote sources already have exactly one function and never
   the real context (`04 section 4.4`). *Cost otherwise*: the facade becomes a security surface with
   no measured behaviour behind it.

Decided here, so the owner need not: refused links live in `LINK` with `status` (one query away from
the active ones); the diacritic fold stays off until the 150-season arm runs (`01 I8`); `punct-join`
variants are not shipped (they serve nyaa's index, not stub's merging, `01 case 31`); anizip's row stays
unscored for scalars (parity, `01 open problem 8`) while the count vote reads classes so its exact count
wins where a DECLARED class should; the engine loads behind the flag until step 3 rather than for every
cold load (a 22.1 MB download, `00`); the two-witness bar applies to the WINDOW (trimming) and not to a
date-proven pair (a pair lands only on an existing member row inside `1..runLength`, so it can add no
row, `01 I9`); no positional loan without a pair (MC-3); `count-sum` and C4 do not exist; a `Slot` is
keyed `<clusterId>#<number>` for numbered rows and `<clusterId>#s:<lowest uri>` for specials, accepting
that a renumbering re-keys a row (today's modal keys rows on the number already, `04 section 2.3`).
